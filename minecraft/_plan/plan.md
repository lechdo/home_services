# Plan — service minecraft

Contexte et décisions d'architecture actées le 2026-08-17 (voir aussi `minecraft/CLAUDE.md`) :
- Pilotage du **conteneur** uniquement (machine hôte toujours allumée) — pas de Wake-on-LAN.
- Hébergement sur le second serveur (`192.168.1.109`), sous réserve de vérification RAM/CPU disponible (phase 0).
- Édition **Java uniquement** (TCP 25565).
- Authentification du panel via une mini-app avec vrais comptes (pas de Basic Auth edge).

RAM disponible confirmée par l'utilisateur (2026-08-17) : 64 Go sur le second serveur — large marge au-delà des 2-4 Go typiquement nécessaires à Paper, en plus de paperless/actual-budget déjà présents.

## Phase 0 — Vérifications préalables

- Vérifier la RAM/CPU réellement disponible sur `192.168.1.109` (`free -h`, `docker stats` des conteneurs déjà présents : paperless, actual-budget) avant d'y ajouter Minecraft. Un serveur Paper avec quelques joueurs consomme facilement 2-4 Go de RAM à lui seul — à comparer à la marge restante. Si la marge est insuffisante, revoir la décision d'hébergement (troisième machine dédiée) avant de poursuivre.
- Vérifier côté routeur/box que le pare-feu IPv6 autorise déjà (ou peut être étendu à) le port TCP 25565 entrant, en plus des 80/443 déjà ouverts (cf. `deploiement-raspberry.md`). Étape manuelle, hors dépôt.
- Décider de la version/modpack Minecraft visée (vanilla/Paper vierge, ou plugins spécifiques) — impacte la config de l'image mais pas l'architecture ci-dessous.

## Phase 1 — Serveur Minecraft (conteneur) — **implémentée (2026-08-17), pas encore testée avec la vraie image itzg/minecraft-server**

- Image recommandée : `itzg/minecraft-server` (TYPE=PAPER par défaut), le standard de facto pour ce cas d'usage — gère le téléchargement/mise à jour du jar serveur, l'acceptation de l'EULA, l'arrêt propre (SIGTERM → sauvegarde), et une configuration entière par variables d'environnement plutôt qu'en éditant `server.properties` à la main.
- Un dossier par map sous `minecraft/maps/<nom>/` (ex. `maps/survival/`, `maps/creative/`) — chacun est un dossier de données Paper complet et autonome, monté sur `/data` dans le conteneur. Une map de départ suffit pour démarrer (`maps/survival/`), les autres se créent en copiant simplement un nouveau dossier vide (le serveur le génère au premier démarrage).
- `compose.yaml` : port de jeu publié sur l'IP LAN du second serveur (`192.168.1.109:25565:25565/tcp`), jamais `127.0.0.1` (service sur un hôte distinct d'edge, même contrat que paperless/actual-budget).
- Pas de `provisioning/` : la config du serveur (variables d'env, `server.properties`) est déjà versionnée via `compose.yaml`/`.env`, pas créée dynamiquement via une API à déclarer séparément (cf. `protocole-donnees.md`).

## Phase 2 — Panel de gestion (site de contrôle) — **implémentée et testée en conditions réelles (2026-08-17), hors itzg/minecraft-server**

- **Testé réellement** : `docker build` de `panel/`, lancé face à un vrai `docker-socket-proxy` (réseau Docker dédié, socket réel de l'hôte) — cycle complet login → sélection de map → démarrage → vérification du bind mount réellement créé (`docker inspect`) → arrêt → changement de map à l'arrêt → redémarrage → nouveau bind mount confirmé. L'image `itzg/minecraft-server` a été remplacée par `alpine:3.20` (`tail -f /dev/null`) pour ce test, uniquement pour éviter de télécharger/démarrer un vrai serveur Java — la logique testée (création/suppression/inspection de conteneur, bind mount dynamique) est strictement celle utilisée en production, indépendante de l'image.
- **Bug réel trouvé et corrigé** : `docker.DockerClient(base_url=...)` se connecte immédiatement à la construction pour négocier la version de l'API — si le client était créé au chargement du module (comme écrit initialement), tout le panel plantait au démarrage tant que `docker-socket-proxy` n'était pas encore prêt (course normale au démarrage de `docker compose up`), y compris pour `/login` qui n'a rien à voir avec Docker. Corrigé par une initialisation paresseuse (`docker_client()`, une fonction plutôt qu'une variable globale construite à l'import), avec la version d'API fixée explicitement (`version="1.44"`) pour éviter la négociation à chaque appel.
- **Second bug réel trouvé et corrigé** : un gestionnaire d'erreur générique qui redirige vers `/` quand Docker est inaccessible bouclait indéfiniment, parce que la route `/` elle-même appelle Docker (`server_status()`) et levait la même erreur. Corrigé en rendant `server_status()` résiliente par elle-même (état `"unknown"` affiché proprement dans le tableau de bord) — le gestionnaire d'erreur générique ne sert plus qu'aux routes d'action (`/start`, `/stop`, `/select-map`), qui redirigent ensuite vers un tableau de bord qui, lui, ne plante jamais.
- **Pas encore fait** : test avec la vraie image `itzg/minecraft-server` (téléchargement de l'image, montée effective du monde, arrêt propre SIGTERM — l'image est conçue pour sauvegarder le monde proprement à l'arrêt, contrairement au conteneur de test) ; création des comptes réels (~10 personnes) ; déploiement sur le second serveur physique.

- Petite application (dans l'esprit minimaliste de `wol/app/app.py` : peu de dépendances, pas de framework lourd) exposant :
  - Statut actuel (map active, en cours d'exécution ou non).
  - Bouton démarrer / arrêter.
  - Sélecteur de map (liste des dossiers présents sous `maps/`), désactivé si le serveur tourne (changer de map implique un redémarrage).
- Le panel ne parle jamais directement à `docker.sock`. Il passe par `docker-socket-proxy` (`tecnativa/docker-socket-proxy`), sur le réseau Docker interne du projet, avec les portées minimales nécessaires (containers + réseaux, lecture et écriture ciblée — pas d'accès images/volumes non utilisé ici).
- Démarrer/arrêter = start/stop du conteneur existant. Changer de map = recréer le conteneur avec un nouveau bind mount `/data` (le SDK Docker du panel gère cette recréation directement, sans passer par la CLI `docker compose`).
- Port HTTP local du panel : `8086` (prochain port libre après edge/bitwarden 8081, paperless 8082, actual-budget 8083, vikunja 8084, wol 8085 — convention du dépôt).

## Phase 3 — Authentification du panel — **implémentée et testée en conditions réelles (2026-08-17)**

- Sessions + mots de passe hashés (bcrypt), ~10 comptes créés à la main dans un fichier (pas de base de données dédiée nécessaire à cette échelle), pas d'auto-inscription — même logique que vikunja (registration désactivée après création manuelle des comptes). `panel/manage.py add|remove <username>` (exécuté via `docker compose exec panel ...`).
- **Testé réellement** (même session que Phase 2) : création d'un compte via `manage.py`, connexion, cookie de session signé (Flask, `SECRET_KEY`), accès protégé aux routes d'action, déconnexion.
- Cookie de session marqué `Secure` (n'est envoyé par le navigateur que sur une connexion HTTPS) — cohérent avec l'accès prévu via `https://minecraft-jvince.duckdns.org/` (edge termine le TLS ; le hop HTTP interne edge→panel ne change rien à ce que voit le navigateur). **Point de test à refaire une fois déployé derrière edge réel** : un test en HTTP direct (sans edge) ne peut pas valider ce comportement, seul un test via le vrai sous-domaine HTTPS le peut.
- Pas encore fait : créer les ~10 comptes réels ; journalisation de qui démarre/arrête le serveur (pas implémenté, pas demandé explicitement — pourrait s'ajouter facilement si besoin, ex. un log applicatif simple).

## Phase 4 — Intégration edge — **implémentée et testée en conditions réelles (2026-08-17)**

Déployée en production sur le Pi et validée de bout en bout — détail complet dans `edge/_plan/plan.md` phase 12. Résumé : certificat Let's Encrypt de production émis pour `minecraft-jvince.duckdns.org`, panel accessible en HTTPS public, port de jeu 25565 accessible publiquement sans configuration de pare-feu supplémentaire (surprise par rapport à l'hypothèse initiale), test réel d'un handshake protocole Minecraft depuis l'extérieur du réseau du foyer réussi (réponse du vrai serveur Paper).

**Correctif du 2026-08-17 (phase 13 côté edge)** : timeout signalé par l'utilisateur en connexion via le nom de domaine (fonctionnait avec l'IP directe) — cause : A record factice (`192.0.2.1`) partagé avec les sous-domaines web, qui piège un client Minecraft Java (pas de bascule IPv4/IPv6 façon navigateur). Corrigé en sortant `minecraft-jvince` du DDNS partagé vers un enregistrement AAAA seul, sans aucun A — voir `edge/_plan/plan.md` phase 13 pour le détail complet et la procédure. Aucune action requise côté routeur (déjà vérifié Phase 4/12 : le port 25565 est joignable publiquement sans configuration supplémentaire).

Deux changements côté `edge`, documentés ici mais à réaliser/valider dans `edge/_plan/plan.md` et `architecture.md` (ce service n'a pas le droit de modifier son propre routage, cf. contrat d'intégration) :

- **Panel (HTTPS)** : nouveau `edge/nginx/conf.d/minecraft-panel.conf`, calqué sur `actual-budget.conf`/`paperless.conf` — `proxy_pass http://192.168.1.109:8086`, `proxy_connect_timeout` court, page d'indisponibilité dédiée (`error-pages/minecraft-panel-unavailable.html`) si le panel ou le second serveur ne répond pas. Sous-domaine DuckDNS : `minecraft-jvince.duckdns.org` (déjà fourni), à ajouter à `DUCKDNS_SUBDOMAINS` dans `edge/.env`.
- **Port de jeu (TCP brut, L4)** — premier usage du module `stream` de nginx dans ce dépôt :
  - edge ne monte actuellement aucun `nginx.conf` personnalisé (il utilise celui livré par l'image `nginx:1.27-alpine`, qui inclut seulement `conf.d/*.conf` dans le bloc `http {}`). Un bloc `stream {}` doit vivre au niveau racine de `nginx.conf`, pas dans `conf.d` — il faut donc fournir un `nginx.conf` complet (repris du défaut de l'image + ajout du bloc `stream { include /etc/nginx/stream.d/*.conf; }`), monté en plus de `conf.d/`.
  - Nouveau fichier `edge/nginx/stream.d/minecraft.conf` : `listen 25565; proxy_pass 192.168.1.109:25565;` (+ `proxy_connect_timeout` court, même raisonnement que pour le HTTP : le conteneur peut être arrêté).
  - Pas de page d'erreur possible sur ce port (protocole binaire, pas HTTP) — le client Minecraft affichera son échec de connexion natif.
  - Le sous-domaine `minecraft-jvince.duckdns.org` pointe vers l'IPv6 d'edge comme toujours (rien à changer côté `sidecar-ddns`, il gère déjà tous les sous-domaines de `DUCKDNS_SUBDOMAINS` en une fois) — le port 25565 est distinct du panel HTTPS mais sur le même hôte/la même IP.
- **Fait (2026-08-17)** : tous les fichiers ci-dessus écrits (`edge/nginx/nginx.conf`, `edge/nginx/stream.d/minecraft.conf`, `edge/nginx/conf.d/minecraft-panel.conf`, `edge/nginx/error-pages/minecraft-panel-unavailable.html`, `edge/compose.yaml` mis à jour, `DUCKDNS_SUBDOMAINS` mis à jour) — voir `edge/_plan/plan.md` phase 12 pour le détail. **Validé réellement** : `nginx -t` réussit avec la config complète d'edge (nouveau `nginx.conf` + tous les `conf.d/*.conf` existants + le nouveau `stream.d/minecraft.conf`), certificats de test générés à la volée pour la vérification — aucune régression détectée sur les blocs HTTPS existants (bitwarden/paperless/vikunja/actual-budget). `docker compose config` validé côté `edge` et côté `minecraft`.
- **Pas encore fait** : déploiement réel sur le Pi (ce test a été fait avec l'image `nginx:1.27-alpine` en local, pas sur la machine cible) ; émission du certificat Let's Encrypt ; ouverture du port 25565 au pare-feu de la box.

## Phase 4b — Création de map, difficulté, plugins depuis le panel — **implémentée et testée en conditions réelles (2026-08-17)**

- **Contexte** : besoin exprimé par l'utilisateur après le déploiement initial — créer une map directement depuis le panel (plutôt que `mkdir` manuel en SSH), régler la difficulté, et gérer deux plugins Paper (autorisations en jeu, tombe récupérable à la mort).
- Volume `maps/` du panel passé en lecture-écriture (`compose.yaml`) — nécessaire pour créer des dossiers de map et copier des plugins depuis le panel.
- **Difficulté** : persistée par map dans `panel-data/state.json`, passée en variable d'environnement `DIFFICULTY` au conteneur créé par `start_server()` — le conteneur est recréé si la difficulté demandée diffère de celle avec laquelle il tourne déjà (même mécanisme que le changement de map), pas seulement redémarré.
- **Plugins** : catalogue restreint à deux entrées (LuckPerms, GravesX — le successeur activement maintenu du plugin "Graves" original de Ranull, trouvé après une recherche : le dépôt GitHub d'origine n'existe plus, le projet vit maintenant sous ce nom sur Modrinth/GitHub). Récupérés via l'API Modrinth (`GET /v2/project/<slug>/version?loaders=["paper"]`, toujours la dernière version compatible Paper) plutôt qu'une URL de jar figée — mis en cache une fois (`panel-data/plugin-cache/`), copiés dans `maps/<nom>/plugins/` à l'activation, jar retiré à la désactivation.
- **Testé réellement** (docker-socket-proxy + socket Docker réel, comme Phase 2) : création de map (rejet des noms invalides et des doublons vérifié), réglage de difficulté persisté et reflété dans le conteneur recréé, téléchargement réel d'un jar LuckPerms depuis Modrinth (~1,5 Mo) et copie dans le dossier de plugins de la map, activation/désactivation, garde-fous (aucun de ces trois réglages n'est modifiable serveur démarré).
- **Pas encore fait** : test avec la vraie image `itzg/minecraft-server` (vérifier que Paper charge effectivement les plugins copiés et applique la difficulté au démarrage) ; téléchargement réel de GravesX (seul LuckPerms a été testé, le mécanisme de récupération est strictement identique pour les deux).
- **Troisième plugin ajouté (2026-08-17)**, suite à une demande explicite : **Thizzy'z Tree Feller** (couper un arbre entier d'un coup, `thizzyz-tree-feller` sur Modrinth, 64k téléchargements) — résolution de version testée réellement (résout bien un jar `TreeFeller-1.30.2.jar` via l'API Modrinth), déployé sur le second serveur.
- **Quatrième et cinquième plugins ajoutés (2026-08-17)**, suite à une demande explicite parmi les suggestions faites : **VeinMiner** (miner un filon de minerai entier d'un coup, `veinminer` sur Modrinth) et **EssentialsX** (`/home`, `/tpa`, `/kit`, `/warp`, `essentialsx` sur Modrinth) — résolution de version testée réellement pour les deux, déployés sur le second serveur.
- **Suggestions restantes, pas implémentées** (en attente de décision) : WorldEdit (construction rapide, à restreindre via LuckPerms déjà en place), CoreProtect (journalisation/rollback des modifications de blocs), Chunky (pré-génération du monde), BlueMap/Dynmap (carte web en direct).

## Phase 4c — Affichage de la version Minecraft/Paper — **implémentée et testée en conditions réelles (2026-08-17)**

- **Contexte** : besoin exprimé par l'utilisateur — voir la version du serveur (Paper) et la version Minecraft directement sur le panel.
- **Format confirmé en démarrant réellement un `itzg/minecraft-server` (TYPE=PAPER)** : Paper écrit `Starting minecraft server version <mc>` et `This server is running Paper version <paper> (Implementing API version <api>)` dans `<map>/logs/latest.log`, dès le tout début du démarrage — fichier qui persiste après l'arrêt du conteneur (bind mount, pas de volume éphémère).
- **Décision** : lu directement dans ce fichier par le panel (déjà accessible via son montage `maps/`) plutôt que via l'API Docker (logs de conteneur) — évite d'élargir les droits de `docker-socket-proxy` (pas de `LOGS`/`EXEC` à activer) et fonctionne même serveur arrêté ou conteneur supprimé.
- **Testé réellement de bout en bout** : démarrage d'un vrai serveur Paper via le panel (pas un `alpine` de substitution comme pour les tests précédents), attente du démarrage complet, vérification que le tableau de bord affiche bien "Minecraft 26.2 · Paper 26.2-112-main@... (Implementing API version 26.2.build.112-stable)".

## Phase 4d — Dynamisme visuel et auto-rafraîchissement — **implémentée et testée en conditions réelles (2026-08-17)**

- **Contexte** : besoin exprimé par l'utilisateur — un indicateur visuel pendant le démarrage/l'arrêt, un indicateur allumé/éteint, et la question de savoir si la page se rafraîchit seule (elle ne le faisait pas).
- **`/start` et `/stop` rendus asynchrones** : `container.stop(timeout=60)` bloquait la requête HTTP jusqu'à 60s (arrêt propre, sauvegarde du monde), sans aucun retour visuel entre-temps — constaté directement par l'utilisateur (source du besoin). Exécutés désormais dans un thread à part (verrou global simple, un seul conteneur géré par ce panel), la route répond immédiatement.
- **État "starting" distinct de "running"** : Docker rapporte "running" dès le lancement du process, mais Paper met encore 30-90s à charger le monde avant d'accepter des connexions (confirmé en conditions réelles à la Phase 4c). `server_ready()` vérifie la présence de `]: Done (` dans `logs/latest.log` de la map en cours — état "starting" tant que cette ligne n'y est pas.
- **Nouvelle route `GET /status`** (JSON, protégée par login) — interrogée par un petit script JS (`fetch`, toutes les 3s, pas de framework) qui met à jour l'indicateur d'état (point statique allumé/éteint ou anneau animé en transition), la ligne de version, et l'attribut `disabled` des formulaires (map/difficulté/plugins) — sans recharger la page.
- **Testé réellement de bout en bout** (vrai `itzg/minecraft-server`, pas de substitut) : `/start` répond en ~50ms (au lieu de bloquer), transition `absent → starting → running` observée par polling successif (~40s, cohérent avec un vrai boot Paper), version affichée automatiquement dès `running`. `/stop` répond en ~70ms, transition `running → stopping → stopped` observée (~6s ici, dépend du monde à sauvegarder). Garde-fou vérifié : `select-map` refusé pendant `starting`.

## Phase 4e — Minuteur de session + notifications in-game (RCON) — **implémentée et testée en conditions réelles (2026-08-18)**

- **Contexte** : besoin exprimé par l'utilisateur — un minuteur de 2h qui arrête le serveur après démarrage, un bouton pour le renouveler, et des notifications aux joueurs (15/10/5 min avant l'arrêt).
- **Réseau Docker dédié** : `compose.yaml` nomme désormais explicitement son réseau par défaut (`minecraft_net`) — nécessaire pour que le conteneur du serveur, créé dynamiquement par le SDK Docker (`network=NETWORK_NAME` dans `start_server()`), soit joignable par le panel via RCON par simple nom de conteneur (résolution DNS Docker), sans jamais publier le port RCON sur l'hôte/LAN.
- **RCON activé à la création du conteneur** (`ENABLE_RCON=true`, `RCON_PASSWORD` généré une fois via `secrets.token_hex` et persisté dans `state.json`, `RCON_PORT=25575`).
- **Bug réel trouvé et corrigé** : la librairie tierce `mcrcon` (initialement utilisée, ajoutée à `requirements.txt`) appelle `signal.signal(signal.SIGALRM, ...)` dans son constructeur pour implémenter son paramètre `timeout` — ce qui lève `ValueError: signal only works in main thread of the main interpreter` dès qu'on l'instancie hors du thread principal. Le thread de fond du minuteur (`session_watchdog`) n'est *jamais* le thread principal, donc **toutes les notifications échouaient silencieusement** (avalées par le `try/except Exception: pass` autour de l'appel RCON) — constaté uniquement en testant réellement le cycle complet avec un faux serveur RCON, pas en lecture de code. Corrigé en retirant la dépendance et en écrivant un client RCON minimal à la main (`rcon_command()`, protocole Source RCON trivial, thread-safe par construction) — `mcrcon` retiré de `requirements.txt`.
- **Minuteur** : `state.json` stocke `session_expires_at` (épuisé) et `session_notified` (seuils déjà envoyés, pour ne jamais notifier deux fois). `start_server()` appelle `start_session_timer()` à chaque démarrage (recréation ou simple `container.start()`), remettant la fenêtre à 2h pleines. Nouvelle route `POST /renew-session` (bouton dédié dans le panel) fait la même chose à la demande, avec confirmation à la fois par message flash et par notification in-game.
- **`session_watchdog`** : thread de fond unique (même pattern que `run_in_background` pour start/stop), vérifie toutes les 10s le temps restant tant que l'état réel est `running` (pas `starting` — pas de compte à rebours tant que Paper charge encore le monde). Diffuse un message (`say ...` via RCON) aux seuils 15/10/5 minutes, puis déclenche l'arrêt automatique (réutilise `run_in_background("stopping", stop_server)`, donc l'UI reflète correctement l'état `stopping`) à échéance. Une échéance manquante alors que le serveur tourne (ex. serveur démarré avant l'ajout de cette fonctionnalité) repart sur une fenêtre pleine plutôt que de tourner indéfiniment sans limite.
- **Panel** : ligne « Arrêt automatique dans : Xh YYmin » (repliée si non pertinente) et bouton « Renouveler (+2h) », tous deux mis à jour par le polling JS existant (`/status`, toutes les 3s) sans recharger la page — même mécanisme que pour l'état démarrage/arrêt.
- **Testé réellement de bout en bout** (docker-socket-proxy + socket Docker réel, comme Phases 2/4b) : image de substitution (comme pour les tests précédents, un vrai `itzg/minecraft-server` n'est pas nécessaire pour valider cette logique) simulant un serveur RCON minimal — cycle complet démarrage → minuteur persisté dans `state.json` → trois notifications RCON reçues et confirmées côté « serveur » aux bons seuils → arrêt automatique déclenché à échéance → `/renew-session` vérifié en cours de partie (remise à une fenêtre pleine + notification de confirmation reçue). C'est ce test de bout en bout qui a révélé le bug `mcrcon`/thread ci-dessus.
- **Pas encore fait** : test avec la vraie image `itzg/minecraft-server` (vérifier que son implémentation RCON réelle se comporte comme le mock utilisé ici — le protocole Source RCON étant standard, aucune divergence attendue) ; déploiement sur le second serveur physique.

## Outils suggérés (récapitulatif)

| Besoin | Outil | Pourquoi |
|---|---|---|
| Serveur Minecraft | `itzg/minecraft-server` (image Docker) | Standard de facto, gère EULA/update/arrêt propre, config 100% par variables d'env |
| Isolation de l'accès Docker | `tecnativa/docker-socket-proxy` | Évite d'exposer `docker.sock` brut à une app accessible depuis Internet |
| Panel (start/stop/changement de map) | App maison minimaliste (style `wol/app/app.py`) + SDK Docker | Cohérent avec la philosophie DIY du dépôt, pas de dépendance lourde |
| Auth panel | bcrypt + sessions, comptes statiques | ~10 comptes fixes, pas besoin d'un IdP (Authelia jugé disproportionné pour cet usage) |
| Routage jeu (TCP 25565) | Module `stream` de nginx (déjà dans l'image `nginx:1.27-alpine`) | Garde `edge` comme point d'entrée unique même pour un protocole non-HTTP, sans nouvel outil |
